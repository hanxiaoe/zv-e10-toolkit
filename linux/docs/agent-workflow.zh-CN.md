# AI Agent：会话操作与故障处理

**简体中文** | [English](agent-workflow.md)

Agent 在连接前先读根目录 [AGENTS.md](../../AGENTS.md)，Jiritsu 操作同时读 [Jiritsu 说明](jiritsu.zh-CN.md)。以下规则来自实际踩坑；它们不意味着所有 USB 故障的原因都已查明。

## 连接前完成准备

先在普通用户权限下检查解释器、依赖导入、toolkit 路径及 `--help`，再请求一次管理员启动。整个任务复用同一个服务端和请求队列，不为每个读取另开连接。先看 `state.json`：只有 `ready` 才发下一条请求或让机主操作菜单。默认在最后一个操作完成后空闲 600 秒关闭；--idle-timeout 3600 可延长到一小时，正在执行长备份的时间不计入空闲。

在现有只读客户端依次执行：

```sh
busybox --list
busybox cat /proc/mounts
busybox cat /proc/meminfo
busybox cat /proc/self/status
```

这是相机内命令，不是在电脑终端直接执行。先核对 applet 清单，不能照搬桌面 Linux 的 `id`、`df`、`stat`、`free`；实测相机没有 `id`/`df`。`/proc/self/status` 显示执行 cat 的进程身份；需要核对常驻 shell PID 时，应由后端在同一 shell 内明确读取该 PID 的状态，不能混淆两者。

`/proc`、`/sys` 是动态伪文件，应让运行中的 shell 执行 cat 后取回输出。GET_FILE 按普通文件方式读取可能返回空内容；不能据此认定 root 丢失或进程死亡。Jiritsu 会话读路径会拒绝直接读取这两类路径。

## 中转目录与分块

目录名不能证明它在 RAM。实测 `/tmp_network` 是上限 1 MiB 的 tmpfs，而 `/tmp` 在 eMMC 上。原 tmpfs 还要保存命令、结果，不能直接放满 1 MiB 的数据块。公开备份默认使用 512 KiB，不应直接改大。

大分块实验使用另建的独立 8 MiB tmpfs，命令留在原目录、数据使用新挂载。先核对可用/可回收内存、精确挂载点、容量和目录内容，最后卸载并删掉挂载点。不扩大原有共享挂载，不把数据块转存闪存，不操作其他会话的目录。

4 MiB 分块已完成一次用户区+B0/B1 备份，总耗时 940.956 秒，平均 1.989 MiB/s；逐块及主机重读校验通过。正式 raw-backup 动作现支持 chunk_kib=4096，自动管理挂载；该集成另经离线失败测试。默认仍为 512 KiB，普通任务不应临时拼装研究入口。

## 报错时保留证据，区分原因

| 现象 | 应做的事 |
|---|---|
| 电脑缺依赖或路径错误 | 连接前修正；不要靠反复管理员启动试错 |
| 命令被拒绝或 applet 不存在 | 查看响应和会话状态；不能直接称为 USB 断联，不重复注入 |
| GET_FILE 读取 /proc 返回空 | 改用 shell cat，不据此判断权限或进程存活 |
| 共享 tmpfs 空间不足 | 停止增大分块；不改用 eMMC 目录，不绕过容量检查 |
| USB 超时、短读、哈希不同、写入状态不明 | 停止后续修改，保留响应/状态/部分数据，不盲目重试 |
| 线插着但系统没有 USB 设备 | macOS 可用 `ioreg -p IOUSB -w 0` 核对枚举；必要时请机主拔插一次。不能据此认定 RAM shell 已死 |

预期内的只读诊断失败应在事务前检查；研究工具可返回可审阅的失败结果，而不把它变成整个服务退出。正式服务端遇结构化处理异常可能会按保护策略退出，不得宣传“任何错误都保活”。也不能用 catch-all 吞掉异常并强行标为 ready，特别是写入、USB 状态或清理不确定时。

取消备份使用客户端 `--cancel-backup`，等待数据块边界停止和取消结果，不使用 SIGKILL。保留 `.part` 及未完成清单，不能把它们标成完整备份。

## 最后统一清理

顺序必须是：**完成操作和全部校验 → 删除本次临时数据/辅助文件 → 卸载本次独立 tmpfs 并删除挂载点 → 正常关闭服务 → 机主断电结束 RAM shell。**

关闭前 shell 和 USB 都要保持可用；如修改过 `/usr`，先确认已恢复只读。Jiritsu 的关闭实现先删除并确认 `run.sh`、`libJit.so`、`out.txt` 不存在，保留 RAM 子 shell 到断电。不要先杀 shell，再用 GET_FILE 确认清理；这条顺序在实测中反复超时，内部原因仍未知。

客户端的 close 响应只表示接受请求，不表示清理完成。须等 `state=closed`、`service_returned=true`、`loader_files_removed=true`，并确认自建挂载已卸载。旧终端后端检查 `terminal_closed=true`。最后让机主关机、等访问灯熄灭、拔 USB、取电池约 30 秒。

若退出失败，清理标志可能不完整；保留本次状态，不沿用上次的成功标志。不要不经检查就覆盖旧加载器文件。完整备份、独立双遍、原子一致性快照和恢复验证应分别报告；本次 2.03 已验证完整单遍，未验证双遍或恢复。
