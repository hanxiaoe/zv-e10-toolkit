# Jiritsu 持续会话与慢速原始备份

**最新完整单遍实测（2026-11-12）：** 独立 8 MiB tmpfs、4 MiB 分块已读满用户区和 B0/B1，共 1,962,934,272 字节；每块相机/主机 SHA-256 及保存文件的电脑完整重读校验通过。备份动作耗时 940.956 秒（含前置检查、元数据、保存校验及 RAM 挂载清理，不含 USB 会话建立/管理员等待），平均 1.989 MiB/s。整个读取无断联，最后临时挂载与加载文件清理、服务退出均成功。这是单遍运行中备份，双遍及恢复仍未验证。大缓冲由研究封装控制，正式 CLI 默认仍为 512 KiB；下文约 1.3 MiB/s/部分读取记录保留为此前阶段结果。


这是相机 Linux 内的临时执行后端，不修改开机启动流程。实测主机为 macOS。2026-11-12 已通过研究封装实机运行整理后的后端及备份动作；尚未提供正式大缓冲 CLI 集成。连接前先读[会话操作规范](agent-workflow.zh-CN.md)。

## 建立唯一连接

在 `linux/` 完成环境准备后：

```sh
./scripts/run_terminal.sh --backend jiritsu --firmware 2.03 --owner-authorized-exec
.venv/bin/python -B host/zve10_terminal_client.py
```

等待 `state.json` 为 `ready`。默认仍限制为只读命令；经机主授权的写操作还需给服务端加 `--owner-authorized-write`。命令在同一个 shell 执行，保留工作目录及变量，但不是完整 PTY，单条输出限 64 KiB。不要用结构化命令中的 `exit/exec/kill/trap/return` 结束或替换子 shell；客户端输入 `exit` 会关闭服务。

建立后端需要**临时向相机服务工作区上传自有的 440 字节载荷及脚本**，所以不能把整个流程称为“相机端零写入”。载荷在 `helpers/jiritsu-shell/` 有汇编源码和构建脚本，构建哈希与实测二进制一致。命令、结果及数据块放在唯一的、已验证为 tmpfs 的 `/tmp_network` 内存目录；不会安装开机自启 root。

## 慢速原始备份

另一终端复用同一会话：

```sh
.venv/bin/python -B host/zve10_terminal_client.py --timeout 3600 --request-json '{"action":"raw-backup","passes":1}'
# 可选 passes=2，执行独立双遍完整读取。
```

范围为 Linux 暴露的整个 `/dev/nflasha`（1,954,545,664 字节，含间隙及尾部），以及 B0/B1 启动区各 4 MiB；每个设备都核对实时容量。不含 RPMB、OTP/eFuse 或隐藏区域，不提供镜像恢复。

root 每次读取 512 KiB 到内存，通过 Jiritsu 回传，逐块核对相机与主机 SHA-256，保存后再从电脑磁盘独立重读校验。结果位于私密会话目录的 `raw-backup-*`。只有精确长度和保存文件验证通过后，`.part` 才改为正式文件；不把部分数据标成完整。

实测约 **1.3 MiB/s**，用户区单遍预计约 **25 分钟**，双遍约 **50 分钟**，另加元数据和主机校验。这是估算，不保证速度。早期 512 KiB 实验在读取 1,681,915,904 字节后按机主要求中止；随后独立大缓冲已完成全部区域，**2.03 独立双遍仍未验收**。Linux 在运行，可写分区两遍间可能变化，不能要求所有活动数据都相同。

取消时不要强杀进程：

```sh
.venv/bin/python -B host/zve10_terminal_client.py --cancel-backup
```

取消在完整数据块之间处理，保留 `.part` 和未完成/已取消清单，连接继续用于清理。SIGINT/SIGTERM 也请求在边界停止。短读取消已实机验证：保留 8,912,896 字节和未完成清单，主机重读一致，取消后连接可继续。

## 结束和断电

客户端输入 `exit` 或提交 `close`。先删除并确认 `run.sh/libJit.so/out.txt` 不存在，再退出服务；等待 `state=closed`、`service_returned=true`、`loader_files_removed=true`。随后关机、拔 USB、取电池约 30 秒，结束剩余的内存进程。

实测先结束子 shell 再访问服务会导致 GET_FILE 超时；“先清理文件、关闭服务、再断电”的顺序成功。内部原因未确定，不能宣传任意子进程退出均可靠。发生超时可能留下临时文件，应保留状态并核查，不盲目覆盖旧载荷。

## 补充实机验收：独立大缓冲

2026-11-12，保持同一个 root PID，另挂独立 8 MiB tmpfs，在相同 4 MiB 启动区上比较分块，升序/逆序各一次，全部块和完整哈希一致。数据循环速度：512 KiB 为 1.24–1.29 MiB/s，1 MiB 为 1.57–1.60，2 MiB 为 1.75–1.85，4 MiB 为 1.95–2.01。循环数字不含前置容量/目录检查；计入这些开销的单次 4 MiB 总耗时为 512 KiB 5.30–5.39 秒、4 MiB 6.36–6.41 秒。该短测本身没有证明全量速度；后续完整单遍结果见本页开头。

独立 tmpfs 已卸载、挂载点已删除，原 `/tmp_network` 的 1 MiB 限额未改。正式 CLI 默认仍为 512 KiB；本次大缓冲由研究脚本控制，不是已经提供的 CLI 选项。本机没有 `id`/`df` applet，身份用 shell 内 `/proc` 确认，大缓冲要求独立挂载和容量/目录核对。

默认 raw-backup 已实测短读并取消，保留 8,912,896 字节部分文件，主机重读哈希一致，正确标为未完成，取消后连接继续可用；最终清理与服务关闭成功。此结果补充了前述取消的离线测试，仍不构成完整镜像验收。
